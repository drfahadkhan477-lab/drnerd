The five stages

Shipped· 21 edits · scripts/stage0-patch.js

Stabilize what you're already studying on

Nothing structural — the output is still one file you drop in Files and open in Safari. Applied as a re-runnable patch script, so the next ACCSAP export takes the same fixes in one command.

  • Three typefaces embedded as base64 (+250 KB), Google Fonts links removed. Launch with no network went from 13.0s to 1.0s — the stall was the font request timing out, and it hit hardest in exactly the places you study: offline, or behind a hospital portal.
  • ResizeObserver leak closed. 41 created, 41 disconnected across 41 renders; previously they accumulated one per render forever.
  • Ink rounded to 4 decimals and simplified with Ramer–Douglas–Peucker. Measured 12.4× smaller on a 200-point stroke, sub-pixel accurate.
  • Practice no longer reschedules. A chapter drill records an attempt and feeds the mastery rings; only the review queue moves a due date.
  • The review log now exists — every answer and rating, with the card's state before it was rescheduled. Pulled forward from Stage 2 because it can't be backfilled.
  • navigator.storage.persist() requested at boot; the Progress screen now shows persistence state, log size and backup age, with a nudge every 150 answers.
  • Question count reconciled to 638, and the previously dead logRated() counter wired up.
Verified21/21 edits applied and asserted, 24 behavioural checks passing, zero console errors, zero network requests on launch. Search, Rhythm Lab, notes, figures and ink all re-tested after patching.

Make it a real PWA

The browser was rebuilding 25 MB of base64 on every launch whether or not you opened the question it belonged to. That was the memory ceiling, the storage ceiling and the reason there was no real offline story. Splitting content from code fixed all three at once — measured, not estimated:

And the splash now covers the remainder instead of a blank screen.
  • 408 figures extracted to real files, referenced by URL and cached by the service worker. base64 costs 4 bytes per 3, so 24.05 MB inline became 18.03 MB on disk — 6 MB of that was encoding overhead alone. Every figure is decoded, written, read back and byte-compared, because an extraction that silently drops one wouldn't surface until revision week.
  • The home screen now fetches zero figures, and opening a question fetches only its own. That is the memory number above, in one sentence.
  • Questions to content/questions.json — 1.66 MB, loaded before the app code runs.
  • Service worker, hand-written rather than Workbox: precache the shell, runtime-cache figures. Precaching 18 MB on install would stall a first launch for questions you may never open, and every miss falls through to the network because iOS evicts caches under pressure.
  • Manifest, maskable icons, display: standalone — Add to Home Screen produces an app. Icons are drawn as SVG and rasterised through the headless browser the tests already use, rather than adding an image library for three PNGs.
  • The app code stayed a classic script, deliberately. The obvious move is type="module" with a top-level await, but module scope is not global scope: every top-level binding would stop being reachable by name, which is how all six test suites drive the app. So the loader fetches the content, puts it on window, and only then injects app.js.
  • The single-file build is untouched and still the artifact for the Files-app workflow. A fetch() cannot cross file://, so the PWA has to be served — that is inherent to splitting content out, not a choice made here.
Verified190 checks. All six earlier suites now run against both builds — 171 passing on each — plus 19 new Stage 1 checks covering shell size, content integrity, on-demand figure loading, the vision path still receiving real base64, service-worker activation, and booting with the network cut off.

Deferred, deliberately — the Vite/ES-module reorganisation and the IndexedDB move. The app code is ~240 KB and splitting it buys maintainability, not speed; every measured win above came from moving the content. Doing the rewrite in the same change would have risked all of it for none of the benefit.
Shipped· 10 edits · scripts/stage2-patch.js

Make the rating mean something

The app was asking for an honest self-assessment and then scheduling all four answers identically on first exposure. That's the central promise of a spaced-repetition tool, and it was silently broken.

  • FSRS-5 replaces SM-2 (hand-written, no dependency — src/core/fsrs.js, ~150 lines): difficulty and stability per card, retrievability computed on demand rather than a coarse reps counter.
  • The four buttons genuinely diverge now. Verified in the real rate-row UI, not just the module in isolation: a brand-new card reads Again → tomorrow, Hard → in 2 days, Good → in 4 days, Easy → in 2 weeks — four different dates instead of four copies of the same one.
  • Legacy SM-2 cards migrate on their next review, seeded from their existing interval — no batch pass, no card silently reset to a fresh state. A 14-day-old card landed at 46 days of stability after one further Good, not back at day one.
  • Mastery is now real predicted retrievability — "how likely you'd recall this today" — not reps/3. A card reviewed 400 days ago now reads 18%, not whatever it scored once.
  • Progress screen gained a retention tile (average recall probability across every scheduled card) and a 7-day forecast strip, so a workload spike is visible before it arrives rather than after.
  • Practice/review separation and chapter interleaving for new cards were already in place from Stage 0 and the existing round-robin sampler — nothing further needed there.
Verified10/10 edits applied and asserted; 25 behavioural checks against the live rate-row, scheduling, migration, mastery and stats UI, plus the full Stage 0 + heart/Apex regression suites (54 checks) still passing on top. Deferred: a pre-answer confidence rating and a full calibration/retention-curve chart — genuinely separate features, not blockers on this one.
Shipped — vision and profile· 9 edits · scripts/stage3-patch.js

Give Apex eyes and memory

The system prompt used to tell the tutor it could not see the figure and should ask you to describe it — inverting the teaching relationship on exactly the items where help is worth most. 305 of the 638 questions carry a figure.

  • The figure now goes with the question. Base64 WebP image blocks, verified against a real intercepted request: correct media_type, raw base64 with no data-URL prefix, images ordered before the question text, and each panel labelled "Figure 1 / Figure 2" so you and Apex can refer to the same one.
  • Anthropic only, and it says so. The Groq models this app offers are text-only, so on Groq the original "describe it to me" prompt is preserved verbatim and the header reads "1 figure, not visible to this model". Dropping the image silently and letting the model bluff about a tracing would be worse than not offering the feature.
  • Images never touch localStorage. They are injected at send time only — a saved thread full of base64 WebP would undo the storage discipline Stage 0 spent real work on.
  • A learning profile rides on every turn — chapter accuracy, recent misses, FSRS retention and due load. Apex opens a conversation already knowing where you're soft, instead of only finding out if it thinks to call a tool. A fresh install correctly produces no profile at all rather than a wall of zeroes.
  • Figure-reading discipline in the prompt: say what you actually see before reasoning from it, admit an unclear image, and treat the ACC commentary as ground truth wherever it and the image disagree — the vision docs are explicit that Claude is not built to read complex diagnostic scans.
Verified9/9 edits asserted; 33 behavioural checks including the wire format of a real intercepted request, multi-figure labelling, tool-loop idempotence (images don't stack across iterations), malformed-URL fallback, and the no-persistence guarantee. All three prior suites still green — 112 checks total.

Deferred, deliberately — the Cloudflare Worker key proxy (needs infrastructure you own, and your key works fine today), cross-question thread memory, and the hybrid embedding index. None of them block reading a tracing.
Shipped — Pencil, hero heart, rhythm library· 20 edits · scripts/polish-patch.js

Make the Pencil and the heart feel like the app they're borrowed from

Not a numbered roadmap stage — a directed set of UX requests, applied together because they share code: the rhythm registry the hero, Rhythm Lab and the ECG engine all read from, and the ink pipeline the Pencil work extends.

  • Pencil width now responds to tilt as well as pressure — lay it flatter and the stroke broadens, the way graphite on its side does. Three named sizes (S/M/L) persist per stroke; an old stroke with no size renders exactly as before, since Medium reproduces the original fixed width byte-for-byte.
  • Auto-minimize, opt-in. Once on, the rail collapses a couple of seconds after the Pencil lifts, and the next Pencil touch on a figure or the stem re-expands the rail and starts the stroke in one motion — the part that actually matches Markup, not two separate taps.
  • The hero heart is real anatomy now. The flat SVG valentine is replaced by a small instance of the same Heart3D renderer Rhythm Lab uses — coarser mesh, no interaction, falling back to the old SVG if WebGL2 is unavailable, exactly like Rhythm Lab already does.
  • heart3d.js gained a blood-flow particle system — two gated streams tracing the pulmonary and systemic circuits through the real anatomy landmarks, visible in cutaway and conduction mode, queuing visibly at a closed valve in sync with the leaflet's own animation. Studied technique from a user-provided reference project without copying its code or assets; this is an independent implementation against the existing procedural WebGL anatomy. Because the addition touches several existing sections of the module, it's re-embedded whole this pass rather than patched piecemeal.
  • The hero's ECG strip rotates through a curated, non-repeating playlist of arrhythmias roughly every 11s — deliberately excluding vfib/asystole from ambient home-screen rotation, since those stay teaching content you go looking for, not wallpaper.
  • 15 more arrhythmias (AV blocks, common ectopy, WPW, bundle branch blocks, hyperkalemia, long QT, pericarditis) — merged into the same registry Rhythm Lab, the hero and the answer-feedback blip all read from, taking the library from 12 to 27.

Week 5–6· Ships: iPad, phone and laptop as one

One account, your devices, your data

Sync carries your data — reviews, notes, ink, chats. The question bank and figures stay local on each device, seeded from your own copy. Nothing about the ACC content goes to a server.

  • Supabase: magic-link auth, Postgres for cards and review logs, row-level security. Chosen over the Firebase skeleton in the repo because the review log is fundamentally relational and you'll want SQL over it.
  • Append-only review log = conflict-free sync. Two devices can't disagree about events that already happened. Cards and notes take last-write-wins per field on updated_at; ink syncs per stroke.
  • Offline-first throughout: the local IndexedDB stays the source of truth, sync is a background reconciliation. Losing signal mid-session must never cost you a card.
  • Later, if you want colleagues in: group streaks and per-chapter accuracy comparison, keyed by question ID. Structure without content — anyone joining brings their own bank.

Note on the current repo

drnerd today holds a generic "iOS Learning Platform" skeleton — five Swift files, 216 lines, unrelated to any of this. Since you've chosen the PWA path, the cleanest move is to repurpose the repo rather than work around it, keeping the Firebase scaffold in history in case Stage 4 ever goes native.

What survives untouched

The BM25 index

The KEEP regex protecting -osis terms from over-stemming, and the boost that stops your own short notes being buried under 1,500-character commentaries.

The query weighting

Repeating your words four times against a clipped stem, so retrieval follows what you asked rather than the question you happen to be sitting on.

The teaching prompt

Mechanism first, work the distractors, and admit uncertainty rather than invent a trial citation. Right pedagogy, right safety posture.

The ECG engine

Gaussian PQRST synthesis with rhythm-specific models, deterministic irregularity for AF, reduced-motion aware. Original, offline, and genuinely nice.

Palm rejection

The four-second pen-priority window. Small detail, and the difference between usable and infuriating with a Pencil.

The network error copy

Captive portals, Files-app preview mode, VPN blocks. Written by someone who has debugged an iPad on a hospital network.

Risks worth naming now

  • iOS evicts storage for sites you don't install. Seven days of non-use can clear everything. persist() plus Add to Home Screen is the mitigation, and it's why Stage 1 matters more than it looks.
  • Keep the original export. Everything downstream is derived from it. Back it up somewhere that isn't a browser.
  • Cache Storage is not localStorage. Figures move to a quota measured in gigabytes rather than 5 MB — but iOS still reclaims it under pressure, so the service worker needs a re-fetch path, not an assumption.
  • FSRS needs history. Its parameters are fitted, so the review log has to start before the scheduler does. That's the one item in Stage 2 that can't wait for Stage 2.

Where this stands now

Stage 0 and Stage 2 are shipped, verified against 79 behavioural checks total across three test suites re-run on every subsequent patch. The 3D heart and the Apex rebrand — not originally on this roadmap — landed in between, wired into Rhythm Lab and the chat panel rather than left as a standalone demo.

The 13-second launch turned out to be the font request failing, not the 25 MB payload — which parses in 0.7s. That doesn't cancel Stage 1, but it re-ranks it: the case for splitting the file is now the 82 MB heap, the 5 MB storage ceiling and genuine offline support, not start-up time.

Stage 3 is shipped for the part that mattered: Apex can now read the figure it is being asked about. The Pencil/hero-heart/rhythm-library polish pass landed after it — genuinely a real anatomical heart with live blood flow now, not a cartoon, and a Pencil that tilts, sizes and auto-minimizes like the app it's borrowed the feel from. Then a startup pass: the cold-open blank screen was measured at 5.5 seconds on a throttled CPU, and a loading screen that paints in ~100 ms now covers it.

Stage 1 is shipped. The shell went from 26.2 MB to 566 KB and the heap from 78.6 MB to 4.8 MB — the memory target was ~25 MB, so it landed five times better than planned, because nothing is resident until you open the question. It works offline once installed. Two pieces are deliberately deferred: the ES-module reorganisation and the IndexedDB move, neither of which produced any of the measured wins.

What remains is Stage 4 (cross-device sync), the deferred Stage 1 and Stage 3 pieces, and Stage 5's CI. The open question is not technical: the PWA has to be served from somewhere, and the content is licensed, so it cannot go on a public host. That choice is yours to make before Stage 4 means anything.
