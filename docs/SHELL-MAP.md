## Reading an entry

    - **`name(params)`** — *what it reaches, through everything it calls* · reads … · writes … · DOM … · storage … · net … · clock … · modules … · calls … · wires … · constants … · through its calls: …

- **reads / writes** name the script's state: a top-level `let` (`S`, `LOG`, `CHATS`), a `const` that something changes in place, and the bank's data, which is every name made from a payload as the script loads (`ALL_Q`, `POOL`, `QBYID`). A property is the first one reached: `S.srs`. A write is a rebinding (`aiBusy=true`) or a change inside (`S.srs[id]=…`, `LOG.push(…)`).
- **DOM, storage, net, clock** are the browser's names the item uses itself: `document`, `localStorage`, `fetch`, `Date` and the timers.
- **modules** are calls into a `src/` module or a vendored library, as `Module.member`.
- **calls into** are methods called on a value the script holds in state (`apexAv.setState`, a viewer, a canvas context kept in a variable). What such a method does is not followed, so the item is put with neither the readers nor the writers.
- **calls** are the shell's own functions it calls, or hands on as a value. **wires** are the functions it writes into markup as inline handlers; they run when tapped, so they are no part of the item's reach, and they are counted where the map works out which functions a screen owns.
- **constants** are script-level names nothing changes after they are made, and that are not made from the bank.
- The phrase in italics is the item's reach through the shell functions it calls and wires, to a fixed point: *pure* (nothing below), *pure but for the clock*, *reads state*, *changes state*, *calls into an object held in state*, or *reaches the DOM, storage or the network*. **through its calls** names what that adds to what the item does itself.

## What this cannot see

- A call made by a name the script builds while it runs: `window[name]()`, a handler attribute assembled from pieces (`onclick="${fn}()"`), `setTimeout` given a string, `eval`, `new Function`. Handlers written whole into markup, `onclick="name(…)"` in a string or a template, are read; so are the ones in the page's own markup outside the script.
- A change made through a value it cannot follow. It follows a local name bound to part of a script-level name (`const c=S.srs[id]; c.due=…` is a write to `S.srs`), a `for…of` over one, the first parameter of a `forEach`/`map`/`filter`/`find`/`some`/`every` callback on one, and the result of `find`/`at`/`get`/`filter`/`slice` on one. It does not follow a value handed to another function as an argument and changed there, a destructured name (`const {srs}=S`), or a value that came back from a call. So a function that passes `S.srs[id]` to a helper that changes it is listed as reading `S.srs`, and the helper as changing nothing of the script's.
- Anything finer than the first property. `S.srs[q.id].due=…` is "writes `S.srs`". A computed first property is shown as `[…]`.
- What a value is. *Pure* means the item uses nothing of the script's or the browser's by name. A function that works only on what it is handed is pure here even when what it is handed is an element, a canvas or a viewer (`apexAtBottom(el)`, `figZoomBy(ps,k)`); read a leaf before choosing between `src/core/` and `src/ui/` for it.
- Which branch runs. Every name a function mentions counts, whether or not the line is ever reached, and "runs as the script loads" takes a called function to run everything it mentions. Both err towards saying more.
- What a function handed to a call does, and when. One handed to a timer, a listener, a promise or an observer is taken to run later; one handed to anything else (`map`, a sort) is taken to run with the call.
- A module's insides beyond its own top level. For a module that sets `root.Name={a,b}` each member is traced to the module's function of that name and what that reaches: the browser's names, the module's own state (a caller of `Memory.add` is listed as changing state, though the state is the module's), and other modules. A member built any other way is given everything the module uses. The vendored libraries are not traced.
- The other inline scripts (the theme and the splash, above the application script), the service worker, the Worker, and anything the split build adds (`scripts/build-pwa.js` writes names such as `LAB_SRC` and `PSW_SRC` onto `window`). Names it could not place are listed at the end rather than dropped.
- Tests. A suite that calls a shell function by name from `page.evaluate`, or cuts one out of the shell by an anchor (`tests/_appcut.js`), depends on that name staying where it is; search `tests/` for the name before moving it.

## A recommended order of extraction

The rule behind the order: move what depends on least first, so each move has less to carry and the next has less in its way. A function can leave the shell for `src/` when everything it uses can be handed to it. That is free for a pure one, cheap for one that only reads state (the state becomes an argument), and a design decision for one that changes state or draws, because the state and the page have to be reachable from where it lands.

## What runs as the script loads

A module written into a slot runs where the slot stands. A function declaration is hoisted, so the shell may call one above the line that declares it. A module is not: a function moved into a module is defined only once the script has run down to its slot. So a function that runs during load, called from a statement above the function's own text, cannot be replaced by a module slotted at the function's position; its slot has to stand above that statement.

Functions the load reaches from above their own text (by the widest reading: everything a called function mentions is taken to run):

- from `INK`'s initializer: `loadJSON`
- from `REF`'s initializer: `invalidateIndex`
- from `S`'s initializer: `validExamDate`
